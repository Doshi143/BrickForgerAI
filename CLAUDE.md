# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

Phase 0 (Foundations) and Phase 1 (Brickifier v1) are done. `core/brickforge` has the LDU lattice, a 44-part verified catalog (bricks/plates/tiles/slopes), placement/collision model, LDR writer, and a `pipeline/` package (voxelize → shell → color-quantize → legalize → LDR) runnable end-to-end via `brickforge-cli mesh.glb --studs N -o out.ldr`.

The legalizer (`pipeline/legalize.py`) implements a scoped-down version of DESIGN.md §4's split-and-remerge idea, with **measured, not assumed**, results (`pipeline/diagnostics.py::count_seam_violations`, compared before/after on the mushroom and bunny test models):
- **Seam-penalty scoring is real and does real work**: penalizes a candidate tile that would exactly reproduce a tile's footprint from the layer below. Cut seam violations from 37.9%→3.2% of parts (mushroom) and 19.6%→0.8% (bunny) — at a real, substantial part-count cost (+67% and +28% respectively). That tradeoff is inherent, not a bug: seam-staggering and Stage B's 3-plate→brick vertical consolidation want opposite things.
- **Multi-restart (randomized whole-layer retiling, Pareto-gated acceptance) is implemented and provably never regresses part count** — but measured **zero effect** on both test models; every random reordering that's tried gets rejected by the Pareto gate before it can help. This is a known, honestly-reported limitation, not a hidden one: whole-layer reordering is a weak substitute for Testuz's actual region-level shatter-and-remerge, which is still not implemented.

Mesh conditioning is minimal (uniform scale + ground it, no watertight repair or thin-feature handling); color quantization is nearest-RGB, not the CIELAB + spatial-smoothing approach in DESIGN.md §3.

**If you touch `legalize.py`'s restart/acceptance logic**: a weighted-sum objective (`parts + weight*violations`) was tried and reverted — it let random restarts "reduce violations" for free by fragmenting a region into many tiny parts (small pieces rarely exactly duplicate a specific rectangle below, so violations drop while part count balloons). Strict Pareto dominance (candidate must not cost more parts) closes that hole. Don't reintroduce a soft trade-off without re-running the before/after measurement.

A first pass at Phase 2 (structural analysis) is also done: `core/brickforge/structure/` builds a connectivity graph (nodes = placed bricks + a virtual `GROUND` node for every y=0 brick, edges = stud/anti-stud connections weighted by shared stud count), finds articulation points and bridges (networkx), and does a **simplified** gravity-load propagation (top-down, splits each brick's cumulative weight among its downward connections in proportion to shared studs, flags connections over an illustrative capacity). This is explicitly **not** the real force analysis DESIGN.md §5 describes — no tension/shear/torque distinction, no empirically-calibrated capacities (the constant in `structure/load.py` is a labeled placeholder).

What it caught immediately, for real, on the Phase 1 example models: the mushroom and bunny both have genuinely unsupported parts. **First diagnosis was incomplete, corrected after the user pushed back** — traced one down to the actual voxel level (the bunny's ear tip: a single-cell gap from coarse voxelization of a thin/steep feature) and concluded that was the whole story, attributing all ungrounded bricks to mesh-resolution limits. The user pointed out that most of the *other* flagged regions looked "decently connected" in the original render and that Studio's own built-in stability check agreed — which turned out to be right. Classified all 111 ungrounded bunny bricks by whether *anything at all* occupies the cell directly beneath their footprint: 71 (64%) had something there, just not from the exact same tile — a legalizer tiling artifact, not a geometry limit. Traced one exactly (see `pipeline/legalize.py`'s connectivity-aware-tiling section below): a wide, well-supported tile can "steal" the cells a narrower, less-supported neighboring region needed to stay connected, purely because greedy tiling with no awareness of what's underneath always prefers more area. Only the remaining 40 (36%) are genuine voxel-level gaps like the ear tip, confirmed both by direct occupancy-grid inspection and by the user independently spotting the ear tip in Studio without being told where to look.

**A real bug in this analysis was found and fixed in the same pass**: the original "floating brick" check (`load.py::propagate_gravity_load`, still present, still useful as a narrower signal) only looks one hop down — does this brick have *any* neighbor directly below it. That misses a brick resting on top of an *already-unsupported* brick: it has a non-empty down-neighbor list, so the single-hop check waves it through, even though its entire support chain is a dead end. This was caught by the repair pass, not by inspection — the first version of the repair loop kept finding new "floating" bricks after each removal round and hit its iteration cap without converging, which was the tell. The fix, `weakpoints.py::find_ungrounded_bricks`, is a single BFS from `GROUND` that only follows edges going strictly upward (an edge to something *above* you doesn't hold you up; only ground or a lower neighbor does) — provably complete in one pass, no iteration needed, and it changed the real numbers: 66→159 ungrounded on the mushroom, 40→111 on the bunny. `report.py`'s `critical_bricks` uses this corrected check; `structure/heatmap.py::classify_bricks` and the `*_heatmap.ldr` files follow from it automatically.

Two repair strategies exist, both starting from `find_ungrounded_bricks`:
- **`structure/repair.py::prune_unstable`** — deletes anything ungrounded. Single-pass, safe, provably complete, but visibly changes the silhouette (holes) wherever it fires — confirmed by the user in Studio on both test models before this was built out further.
- **`structure/bridge.py::bridge_unstable`** (now the default repair used by `examples/structural_report.py`) — connects instead of deleting: drops a straight vertical pillar of 1×1 plates from one point in each ungrounded island down to existing grounded geometry or the baseplate, falling back to `prune_unstable` for whatever still can't connect. **Only a straight vertical pillar can ever create a new graph edge** — side-by-side parts at the same layer never share a stud connection in this catalog (matches real LEGO), so a connector placed next to a gap, however close it looks, does nothing.

**First version of bridging shipped a visible regression the user caught immediately**: an unconstrained pillar happily travels through open air, not just hidden interior, since a shelled/hollow Model's occupancy alone can't tell "empty because hollow interior" apart from "empty because outside the sculpture entirely." Confirmed on the bunny: the ear-tip pillar needed 13 plates and landed on bare ground without touching anything else along the way — 13 plates of exposed pole, not a hidden brace. **Fix**: `mesh_to_model_full` (`pipeline/mesh_to_model.py`) now also returns the pre-shell solid `VoxelGrid`, in the same index space as the final Model (shelling/legalizing never shift or resize the grid), and `bridge_unstable` takes it as an optional `solid_grid` param — every cell a candidate pillar would occupy, including the one it lands on, must be part of the *original* solid silhouette, not just currently unoccupied. Every column in an island's own footprint is tried as a candidate anchor; the shortest fully-interior one wins. Measured effect: mushroom pillars dropped from 1714 (unconstrained) to 274 (interior-only) parts; bunny dropped from 317 to **0** — none of the bunny's ungrounded regions have a hidden route to ground anywhere along their footprint, confirmed empirically, not assumed.

**Hole refill went through two rejected designs before landing on one that's actually honest, and both rejections were caught by the user, not by self-review — worth reading if you touch `structure/refill.py`.**

- v1 required a single cell to be boxed in on all 4 lateral sides. Never fired on either real model. Cause: a cell in the middle of even a small pocket has neighbors that are *also* part of the pocket, not "present" — a per-cell rule can't see pockets bigger than one cell.
- v2 grouped removed cells into connected blobs and accepted a blob if its *boundary-face enclosure ratio* cleared a threshold, capped by blob size. This visibly worked (55/54 cells refilled) — right up until the user asked, reasonably, whether "boxed in by neighbors" actually satisfies "no floating segments." It doesn't: every refilled cell had **zero stud connection underneath it** (if it had one, `find_ungrounded_bricks` wouldn't have flagged it in the first place) and was held only by lateral/top friction. Re-running `analyze()` on the "repaired" output showed those exact cells still critical — the fix hadn't actually fixed anything, just hidden it inside a filename that said "repaired."
- **v3 (current)**: `refill_enclosed_holes` fills bottom-up, one layer at a time, and only ever adds a cell once whatever's directly beneath it (in the model as repaired so far, including cells refilled earlier in the same pass) is *itself already grounded* — not present, **grounded**, checked with the same `find_ungrounded_bricks` definition used everywhere else. A connection to something *above* a candidate cell doesn't hold it up (gravity goes the other way, same reasoning as `find_ungrounded_bricks`'s own docstring), so only "below, or y=0" counts. This is provably correct, not a heuristic: every cell added is reachable from `GROUND` by a real chain of stud connections by construction.

**Measured result on the real models at that point, and it was a clean, honest zero**: v3 refilled **0 cells on both models** given the legalizer as it stood then. Correct, not a failure: bridging already searches every column in each ungrounded island's own footprint for a hidden path to grounded material, so if a pruned cell had genuinely-grounded material directly beneath it, bridging would already have used it. Nothing was left for refill to find *at that point* — see below for why "at that point" matters.

**`pipeline/legalize.py` connectivity-aware tiling — the actual root-cause fix for most of the "legalizer artifact" 64%, added after the classification above.** The traced case: two rows of shell material at the same Y layer (z=14 and z=15), where only z=14 has support at the layer below. Greedy tiling, scanning in raster order with no notion of "underneath," extends a wide tile along the well-supported z=14 row (bigger area = better score, by the only criterion Stage A had) and leaves z=15 to be tiled separately, unsupported — even though a single tile spanning both rows would have connected fine. Fixed two ways, together: an "unsupported cells first" scan order (lets an unsupported cell try to combine with a supported neighbor before a wide greedy tile from the supported side claims that territory first) plus a new `_count_orphaned_parts` metric (parts with zero footprint overlap with the layer below) added *ahead of part count* in the restart-selection comparison — deliberately not Pareto-gated the way the seam-violation objective is: the user was explicit that structural soundness outweighs part-count efficiency, so more parts is an acceptable price here, unlike the seam-violation case (see `legalize.py` module docstring for why fragmentation can't cheaply game *this* particular metric the way it gamed the violations one).

**Measured, and it's a real but partial fix, not a full one — say so plainly if this comes up again**: bunny ungrounded count dropped 111→91 (18%), mushroom 159→142 (11%) — nowhere near the full 71/111 the classification suggested was theoretically fixable. Traced the exact original case again afterward: still unfixed. Root cause: my greedy tiler only ever grows a rectangle from its minimum (x, z) corner toward higher x/z. Since z=14 < z=15, a tile anchored at the unsupported z=15 cell can *never* reach back down to the supported z=14 cell — the "process unsupported cells first" heuristic cannot fix a case where the unsupported cell would need to be reached *by* a tile growing from the supported side, not act as its own anchor. Properly fixing this needs real lookahead (recognizing, before committing to a wide tile, that it will orphan a neighbor) — i.e. actual Testuz-style region shatter-and-remerge, not an ordering tweak. Not attempted; flagged as the next real step if this is revisited.

**Net effect end to end, measured after re-running the full bridge+refill+prune pipeline on top of the improved legalizer**: fewer total holes despite the partial fix, because a smarter baseline needs less repair downstream — mushroom's fully-repaired output actually got *smaller* (4306→4174 parts) even though its unrepaired baseline got slightly bigger (4185→4222), because far fewer pillars were needed (274→92) and fewer prunes (153→140). Bunny's repair still finds 0 bridgeable cells and prunes all 91 remaining — confirming, again, that what's left really is the genuine-gap category (ears, thin features), not more tiling artifacts.

**The real, still-true conclusion for that layer of the work**: what's left after legalize(connectivity-aware) + bridge(interior-only) + refill(bottom-up-grounded) + prune is either genuinely fixed (no external poles, no fake friction-fit patches, every remaining part provably stud-connected to ground) or genuinely pruned. But "provably stud-connected to ground" turned out to be the wrong bar to hold every single brick to — see the next section, which supersedes most of the urgency (though none of the correctness) of everything above.

**The actual root cause of nearly all the holes: `find_ungrounded_bricks` (directed, one private straight-down chain per brick) is the wrong check to drive repair. `find_bricks_outside_main_component` (undirected: is this brick part of the same rigid, interconnected mass as GROUND via *any* path) is the right one, and switching to it eliminated nearly all remaining holes without changing a single line of the legalizer, bridge, or refill logic.**

Caught by the user a third time, with two pieces of independent evidence: the *unrepaired* model didn't look obviously broken except at one spot, and Studio's own built-in stability checker agreed, flagging only ~4 bricks in 2 small clusters — nothing like the 91-159 `find_ungrounded_bricks` was reporting. Checked directly rather than argued back: `find_bricks_outside_main_component` on that same unrepaired bunny returns **exactly 4 bricks in exactly 2 clusters** — matching Studio closely. That's not a coincidence. A directed, single-path "must rest directly on something below, all the way down" model is correct for an isolated tower, but wrong for a dense, richly-interconnected shell, where a brick can be held firmly by neighbors above and to the side — the way a keystone is held by lateral compression, not by resting on the ground itself. `find_ungrounded_bricks` has no way to see that kind of support; undirected connectivity does, for free, because "connected to the ground by *some* path through the structure" is exactly what keystone-style bracing is.

`find_ungrounded_bricks` is kept (`weakpoints.py`) — it's still a correct answer to the question it actually asks, and it's exposed in `StabilityReport.ungrounded_bricks` as an informational-only field — but `report.py::critical_bricks`, `repair.py::prune_unstable`, and `bridge.py::bridge_unstable` were all switched to the new `find_bricks_outside_main_component` (see `weakpoints.py`'s module docstring for the full reasoning; a new regression test, `test_undirected_connectivity_sees_a_keystone_the_directed_check_misses`, constructs the minimal case where the two checks disagree and pins the correct answer). `refill.py` deliberately kept the strict directed check for its own internal "is it actually safe to add this specific cell back" decision — a different question, where being conservative is the right call, unlike deciding what counts as broken in the first place.

**Effect, measured, not assumed**: mushroom needs **zero repair** now — it was always a single connected piece; every one of its 142 "ungrounded" bricks was already properly braced into the main mass, just lacking a private straight-down chain. Bunny drops from pruning 91 bricks to pruning **4** — exactly its 2 genuinely disconnected clusters (the ear-tip island, 3 bricks, and one isolated brick elsewhere), matching Studio's own assessment. `examples/output/mushroom_repaired.ldr` no longer exists (nothing to repair); `bunny_repaired.ldr` is 897 parts (901 baseline − 4 genuinely isolated). The connectivity-aware legalizer work above (§ "connectivity-aware tiling") is still real and still worth keeping — it's what got the mushroom down to zero disconnected components in the first place, and reduces the odds of a future model needing any repair at all — but it's no longer the thing standing between a model and a clean stability report; the criterion fix is.

**Phase 3 (surface refinement) is in progress.** Tiles are done: the catalog now has 8 tile entries matching every plate size except 2×8 (no standard part exists), and `pipeline/surface_refine.py::substitute_tiles` swaps any top-exposed plate for its matching tile. This substitution is structurally always-safe by construction (a tile has the same footprint and bottom-stud coverage as the plate it replaces, and removing top studs can only ever remove connectivity that nothing was using — since the substitution only fires where the top face is already exposed to open air) — confirmed by tests, not just asserted, and wired into `examples/structural_report.py` as the final pipeline step after repair, needing no re-validation loop for that reason.

Slopes are the harder half and caught a real geometry bug before the detection algorithm was even started. Six slope parts were added (3040/3039/3038/3037 upright, 3665/3660 inverted), footprint and height verified from raw `.dat` vertex data the same way the rest of the catalog was. **Unlike every other part in this catalog, a slope's LDraw origin is not at the horizontal center of its own footprint.** `s/3040s01.dat`'s full vertex geometry spans local Z in [-30, +10] — 40 LDU (2 studs) wide as expected, but centered on Z=-10, not Z=0: a genuine 10 LDU (half-stud) asymmetry. The first version of the catalog assumed uniform centering (true for every brick/plate/tile checked) and got this wrong silently — invisible to unit tests, which only checked internal self-consistency, and only caught when the user spotted the resulting non-integer-stud misalignment against plain plates in Studio. `s/3665as01.dat` (the inverted slope's real geometry — `3665.dat` itself is now a "~Moved to" redirect stub to `3665a`) was independently checked and showed the identical Z range, so the same correction was applied to all 6 slope entries rather than re-derived per part.

Fixed with a new `local_offset: (dx, dz)` field on `Part` (`catalog/parts_v1.yaml`, all 6 slopes now carry `local_offset: [0, 10]`), threaded through a new `Rotation.rotate_offset()` (`lattice.py`) and applied in `placement_to_ldraw()` — the offset has to rotate with the part, not stay fixed in world space, since a fixed local-frame asymmetry points a different way depending on which way the part is turned. Verified two ways before considering it done, per this project's established discipline of measuring rather than assuming: (1) computed the rendered bounding boxes by hand for both an unrotated and a YAW_90-rotated slope next to a matching plate and confirmed they land exactly flush, no gap; (2) regenerated `examples/output/slope_alignment_test.ldr` through the real `Model.place`/`save_ldr` API (not hand-written LDU, unlike the first version of this test file) and had the user re-open it in Studio — confirmed visually flush on both pairs, closing out the bug the user's original screenshot caught.

**Staircase detection (`pipeline/slopes.py::substitute_staircase_slopes`) is built, tested, and correct in isolation -- but measured to be nearly inert on the real pipeline output, for a real, pre-existing architectural reason, not a bug in this pass.** It scans brick-height (height_plates==3) blocks for a genuine step-down edge in one of the 4 cardinal directions (top exposed, a strictly-lower-or-empty column beyond the downhill face, an at-least-as-tall column behind the uphill face) and replaces the block in place with the matching upright slope, at the rotation whose tall face points uphill. That rotation mapping was verified empirically before writing any detection logic, the same discipline as the offset fix above: built `examples/output/slope_orientation_test.ldr` (a 2x2 brick immediately adjacent to a 2x2 slope at YAW_0), opened it in Studio, and confirmed the tall face sits on the -Z side, descending toward +Z -- then derived the other 3 rotations from that one fact via the same rotation matrix `rotate_offset` already uses, rather than testing all 4 by hand. Structural safety follows the identical argument as tile substitution (every brick has bottom:full matching every slope's bottom:full, so only TOP connectivity is ever removed, and only where nothing already rests there) -- confirmed, not just argued, by a before/after `analyze()` test and by wiring an equivalent assertion into `structural_report.py` itself, not just the test suite.

**Run on the real turret/mushroom/bunny models, it substitutes zero slopes on all three** (versus 5/115/65 tiles substituted on the same models). Traced, not shrugged off: `mesh_to_model_full`'s output is **898 plates + 3 bricks** for the bunny and **4134 plates + 88 bricks** for the mushroom -- brick-height material is almost entirely absent from what the legalizer actually produces. This is the flip side of a tension already documented above: seam-penalty scoring deliberately staggers tiling between adjacent layers to avoid seam violations, which is nearly mutually exclusive with Stage B's 3-identical-layers requirement for plate-to-brick consolidation. Slope substitution was built to operate on brick-height blocks (matching the catalog's only available slope height), so it inherits this starvation for free -- not a new problem, just a previously-invisible consequence of an already-known, already-accepted tradeoff. Fixing this for real needs either plate-height slope parts (real LDraw parts exist, e.g. "Slope Plate" family -- not yet verified or added to this catalog) or loosening Stage B to consolidate more plates into bricks at the cost of reintroducing more seam violations; neither attempted yet.

**Added a second, 2-plate-height slope tier on top of the above, at the user's request for "small slopes for detail + large slopes where possible."** First finding, from searching brickarchitect.com/BrickLink's slope category rather than assuming: **no standard rectangular LEGO/LDraw slope exists at exactly 1 plate tall.** The shallowest real size is 2 plates (2/3 brick, 16 LDU) -- the "30/31°" family (54200 1×1, 85984 1×2, 7825 1×3, 7835 1×4; the angle name is cosmetic, a rectangular ramp with a true 1-plate rise can't exist at a whole-stud run length). Didn't invent a part, same rule already applied to the missing 2×8 tile.

Second finding, caught by fetching the raw `.dat`/subpart vertex data for all four parts before writing anything to the catalog (same discipline as the local_offset fix above, not repeated by assumption): **this whole family is bottom-anchored, not top-anchored.** Every existing part in this catalog (bricks, plates, tiles, the 3-plate slopes above) has local Y=0 at the part's TOP; these four have local Y=0 at the BOTTOM, extending upward (more negative Y) to the sloped top -- confirmed both by the raw Y ranges (all ≤ 0, the mirror image of every top-anchored part) and directly, by 61409's own official `!HISTORY` line: "2009-03-30 [gregteft] Updated origin to bottom center". Getting this wrong would have silently placed every 2-plate slope one full part-height too high -- invisible for a lone part on a flat floor, wrong the moment it meets a neighbor of a different height, the identical failure shape the local_offset bug above already produced once. Fixed with a new `Part.y_anchor` field (`"top"` | `"bottom"`, default `"top"` so every existing part is unaffected) threaded through `lattice.py::placement_to_ldraw`, which now branches on it instead of assuming top-anchored universally. The family's horizontal centering was checked too, not assumed to match the 3-plate slopes' asymmetric `local_offset: [0, 10]` just because both are "slopes": X is symmetric about 0 at every width (1-4 studs), and Z (the 1-stud run direction) is also symmetric about 0 once corner-rounding from a later "Rounded corners and flattened top" part revision is accounted for -- so this family's `local_offset` is `[0, 0]`, a measured conclusion, not a default left unexamined.

Unlike every substitution before it, the 2-plate tier is a **merge, not a swap**: a 2-tall identical-footprint plate stack is normally two separate placed parts (Stage B only consolidates stacks of exactly 3), so there's no single existing part to swap from. `pipeline/slopes.py::substitute_staircase_slopes` now runs two independent passes -- the original 3-plate swap (generalized to look up `(height_plates, perp_width) -> (part_id, run_length)` instead of a flat width map, so the run length isn't hardcoded to 2 studs anymore, since this new family runs 1 stud) and a new pass that finds vertically-stacked plate pairs (identical footprint, upper's top fully exposed, same step-edge test as the swap case) and replaces both with one slope. The two tiers can never compete for the same source brick -- a `brick`-category object is never also a plate-pair member -- so "prefer a larger slope where possible" falls out for free from running both passes independently, with no explicit tie-break needed. Safety argument is the same shape as before, restated for a pair: the lower plate's own downward connectivity is untouched, the upper plate's top must already be exposed, and the internal stud edge between the merged pair isn't left dangling since both its endpoints are deleted together -- confirmed with a before/after `analyze()` test for the merge path, not just argued. (This did require fixing `examples/structural_report.py`'s own before/after check, which compared `critical_bricks` as raw index sets and asserted part count was exactly preserved -- both invalid once a merge legitimately shrinks the model and shifts indices. Now compares counts, not index sets, and allows count to decrease.)

**Measured, not assumed, and it's a real but modest improvement, not the fix it might sound like:** re-run on turret/mushroom/bunny, the 2-plate tier fires **3 times on the mushroom** (0 before) and **still 0 on turret and bunny**. The underlying hypothesis (this project's plate-heavy output should have far more 2-plate step edges than 3-plate ones) is directionally right -- it went from firing nowhere to firing somewhere -- but genuine, exactly-matching-footprint 2-tall plate pairs sitting at a real step edge are still comparatively rare in what the legalizer actually produces. Loosening Stage B consolidation and the 33°/65°/75°/inverted slope families remain explicitly out of scope for this pass (see `pipeline/slopes.py`'s module docstring).

**The 2-plate tier shipped placed backwards -- a fourth per-family assumption bug, caught by the user in Studio, not by any test.** The orientation logic (`_DOWNHILL_ROTATION`) was derived once, empirically, for the 3-plate family (tall/uphill face at -Z at YAW_0) and then reused unchanged for the 2-plate family under the assumption that "slope" implies a shared facing convention -- the same shape of mistake as the footprint-axis, local_offset, and y_anchor findings above, and it should have been checked independently from the start. Re-fetched `s/7825s01.dat`'s raw ramp geometry: it runs from (Z=-10, Y=-4) -- near this bottom-anchored family's own ground level, the thin/downhill edge -- to (Z=+6, Y=-13.6) -- near full height, the tall/uphill edge. Tall face at **+Z**, not -Z: the mirror image of the 3-plate family. 85984 and 7835 show the identical pairing, so this is a real family-wide fact, not a one-part fluke. Fixed by rotating the 2-plate merge path's chosen rotation 180 degrees (`_OPPOSITE_ROTATION` in `pipeline/slopes.py`) rather than maintaining a second direction table -- both tiers still share one source of truth for "which cardinal direction is which rotation," only the final 2-plate placement gets flipped. Pinned with a regression test asserting the two tiers get *opposite* rotations for the identical downhill direction (`test_both_tiers_fire_independently_in_the_same_model`), not just a single-tier check that could pass by coincidence. All examples (turret/mushroom/bunny/duck) regenerated; substitution counts unchanged (only rotation did), and the user has not yet re-confirmed the fix visually in Studio -- do that before treating this as fully closed, per this project's established two-step "fix, then re-verify visually" pattern.

**A working trial web app now exists in `web/`** (Phase 5's beginning, though payments/auth/queueing are all still absent — see DESIGN.md §9):

- `web/backend/` — FastAPI, adapted from a separate prompt-to-brick backend the user had built. Its own naive greedy voxel coverer was **deleted** and replaced by `app/pipeline/brickforge_bridge.py`, a thin adapter that calls `core/brickforge` (installed editable via `pip install -e ../../core`) and reuses `examples/structural_report.py`'s exact repair sequence. Job API: `POST /generate` → poll `GET /generate/{id}` → `GET /generate/{id}/download`. The pipeline runs in a `BackgroundTasks` task so the poll actually reports incremental phases; the job store is in-memory (trial-scale, not a real queue).
- `web/frontend/` — Next.js 16 (App Router, TypeScript), with the design mockup's color tokens ported verbatim into `app/theme.ts` rather than re-eyeballed. The results page reuses the Phase 0 `viewer/index.html` three.js + `LDrawLoader` setup as a React component (`components/Viewer3D.tsx`), which is what makes real LDraw color codes render as actual brick colors.
- Prompt → image is OpenAI `gpt-image-1`; image → mesh is TRELLIS via a **locally-run** ComfyUI (user-managed, not installed by this repo).

**Colors were genuinely broken end to end, and the root cause was upstream of anything in `core/brickforge`.** Measured, not assumed: the bundled ComfyUI workflow (`app/clients/trellis_workflow_api.json`) is **shape-only** — its node chain runs ImageCond → Sparse → Shape → ShapeCascade → DecodeLatents → Simplify → FillHoles → Trimesh → Export, with no texture/appearance node anywhere. Confirmed against a real prior job output: all 231,917 vertices were the identical gray, RGB (102,102,102), despite the job's own reference image being an obviously brown wooden table. So `pipeline/color.py` was faithfully quantizing "uniform gray" — not a quantizer bug, the color was never in its input. Fixed with `app/pipeline/reference_color.py`, which projects the reference image onto the mesh as per-vertex colors when (and only when) the mesh arrives flat. Two findings worth keeping: (1) the projection **must** map the mesh's bounding box onto the *subject's* pixel bounds, not the whole frame — these are studio-style shots where the subject fills only the middle ~half, and mapping to the full frame projected most of the model onto empty backdrop, turning a brown table mostly dark gray; (2) verified by rendering the result and reading back the actual three.js material colors — 171/315 parts came out `#5f3109` reddish-brown, correct for the subject. It's an orthographic approximation of a three-quarter-view photo (front/back get mirrored colors) and is documented as such; the real fix is adding TRELLIS's texture stage to the workflow, at which point `reference_color.py` stops firing on its own.

## What this project is

A web app: text prompt → physically stable brick sculpture → LDR file + parts list + build instructions.

```
prompt → image gen → image-to-mesh → mesh conditioning → voxelize → shell
       → colour quantize → legalize (tiling) → structural repair ⇄ surface refinement
       → inventory check → build order → LDR / BOM / PDF
```

Scope is **sculpture-style builds**, deliberately not minifig-scale System sets — the latter is an open research problem. Don't let feature requests drift across that line.

Only the mesh→brick half is proprietary. Image and 3D generation are bought-in APIs; do not build them.

## Lattice invariants

All geometry in **LDU** (1 LDU = 0.4 mm). These are exact:

| Quantity | LDU |
|---|---|
| Stud pitch (X, Z) | 20 |
| Plate height (Y) | 8 |
| Brick height (Y) | 24 |

The vertical and horizontal lattices are incommensurable except at one point: **5 plates = 40 LDU = 2 studs.** Every sideways-mounted (SNOT) sub-assembly must return to a 40-LDU boundary to re-mate with the studs-up lattice. This constraint belongs in the data model from the start — retrofitting it is painful.

**LDraw's Y axis is negative-up.** Internal representation is Y-up in integer plate units; convert only at LDR serialization. Do not let the LDraw sign convention leak inward.

Voxels are anisotropic (20×20×8), never cubic. Plates are the base unit; bricks are a *merge optimization*, not a primitive.

The part catalogue table (occupancy footprint per orientation, stud/anti-stud connector positions, finished faces, allowed colours, price, availability) is generated once by parsing the LDraw parts library and then hand-corrected. Never derive part geometry at runtime.

**Footprint axis convention is counter-intuitive — verify, don't assume.** For an official LDraw part named "A x B", the *second* number (B) runs along local X and the *first* (A) runs along local Z — e.g. "Brick 1 x 4" has footprint `(4, 1)` in `[x, z]` terms, not `(1, 4)`. A first cut of `catalog/parts_v1.yaml` got this backwards (read straight off the name) and it silently transposed every rotated/unrotated non-square part 90° from its true rendered footprint — invisible in unit tests (which only checked internal self-consistency), only visible once opened in Studio. Confirmed by fetching and inspecting raw part geometry (`parts/3010.dat`, `parts/3004.dat`, `parts/3001.dat`), not by re-deriving from the naming convention. Square parts are unaffected. If you touch the catalog, re-verify against real `.dat` files, not the name.

**LDraw part origins are top-anchored, not bottom-anchored.** Local Y=0 is a part's *top* (stud surface); it extends down to local Y=+height_ldu at the bottom. A naive reading of "-Y is up" suggests the opposite. Also confirmed by fetching real part files (`parts/3005.dat`, `parts/3024.dat`), not assumed. Getting this wrong is invisible for a stack of uniform-height parts (the per-part shift is constant) and only breaks visibly where parts of different heights meet.

## Pipeline ordering constraints

These orderings are load-bearing; reordering silently degrades output:

- **Colour quantization precedes tiling.** A part spans one colour only. Tiling first forces wrong colours or a field of 1×1s.
- **Shelling precedes tiling.** A solid model is ~40k parts and unsellable. Shell and internal lattice must *share* bricks at junctions, or the skin ends up disconnected from the skeleton.
- **Surface refinement (slopes/tiles) runs after box tiling and loops back into structural analysis.** Every tile or slope substitution deletes stud connections, so each one must be re-validated and may be rejected.
- **Mesh conditioning precedes voxelization.** Un-repaired single-image meshes are non-watertight and carry sub-brick-thickness features; voxelizing them directly is the main source of garbage output.

Two objectives are routinely forgotten and matter more than part count:
- **Vertical seam stagger.** Aligned seams across layers are a crack. Brickwork-style staggering is what lets a sculpture survive being picked up.
- **Articulation points / bridges** in the connectivity graph. Cheap to detect, and they account for most real-world breakage — check these before running the force LP.

Aesthetic parts go on the outward-facing shell only. Never spend part budget on surfaces the user cannot see.

## Architectural rules

**Every pipeline stage is a pure function over serializable artifacts** (`mesh.glb → voxels.npz → model.json → model.ldr`). Tuning means re-running one stage against a cached upstream output hundreds of times; this also buys resumability and a debugging CLI for free. Do not fuse stages or thread mutable shared state through them.

Prototype in Python + numpy. Port to Rust (PyO3) only when the legalization anneal loop measurably bottlenecks, and only that loop — the algorithm will be rewritten many times before it stabilizes.

Long-running work belongs in queue workers, never in a web request. Stages have different resource profiles (GPU for mesh, CPU for brickify) and should be separately schedulable.

Structural capacities live in a config file (`physics.yaml`) and are **empirically calibrated**, not taken from literature — published per-stud values vary, and tension is far weaker than shear.
